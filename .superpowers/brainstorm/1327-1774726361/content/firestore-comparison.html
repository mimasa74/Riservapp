Opzione B vs Opzione C — confronto

Come cambia la struttura Firestore e le conseguenze pratiche

B — Documento per specie
/species/cervo          ← 1 documento

  categories: [
    { id:"ce1", abbattuti:6, ... },
    { id:"ce2", abbattuti:1, ... },
    { id:"ce3", abbattuti:0, ... },
    { id:"ce4", abbattuti:0, ... },
  ]

✓ Lettura: 1 sola query per caricare tutto

✓ Real-time: onSnapshot su 1 doc → aggiornamenti istantanei

✓ Costo: 1 lettura per caricare la specie

✗ Scrittura: aggiornare 1 quadratino = riscrivere l'intero array categories

✗ Conflitti: se due admin toccano due categorie diverse nello stesso istante → una modifica vince, l'altra si perde

C — Documento per categoria (subcollection)
/species/cervo          ← documento padre
  /categories/ce1       ← subdoc
    { abbattuti:6, ... }
  /categories/ce2
    { abbattuti:1, ... }
  /categories/ce3
    { abbattuti:0, ... }
  /categories/ce4
    { abbattuti:0, ... }

✓ Scrittura atomica: aggiornare 1 quadratino = scrivere solo 1 documento piccolo

✓ Zero conflitti: ogni categoria è indipendente

✓ Real-time: onSnapshot per categoria → aggiornamento chirurgico

✗ Lettura: query su subcollection per caricare tutte le categorie

✗ Costo: 4 letture (cervo) o 6 (camoscio per zona) invece di 1

Il fattore decisivo: quanti admin ci sono?

B

1 solo Rettore

Non ci sono mai due persone che modificano contemporaneamente → il rischio conflitti è teorico. L'opzione B è più semplice da implementare e da mantenere. Raccomandato.

C

Più admin in futuro?

Se prevedi di avere più persone che modificano dati contemporaneamente (es. vice-rettore), l'opzione C elimina il problema alla radice. Leggermente più complessa da implementare.

In pratica: con 1 solo Rettore e al massimo 45 capi abbattuti in tutta la stagione, la differenza di costo e complessità tra B e C è irrilevante. La scelta è principalmente di preferenza architetturale.
